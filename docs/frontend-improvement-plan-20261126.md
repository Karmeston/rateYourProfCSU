# 前端改进问题清单与方案（2026-11-26）

本文件交给后续实现者使用。问题来自 2026-11-24 对线上站点（Worker `24da9376`，源码 `e133adf`）的桌面与 375×812 手机视口走查，以及对 `web/`、`shared/` 代码的阅读。本文只记录问题和建议方案，没有改动代码。

## 一、先读：约束与约定

- **免费额度是硬约束**。D1 每天 500 万行读取，Workers 与 Durable Object 各每天 10 万次请求。课程广场完全走静态目录 `data/course-data/public-directory.json`（约 905KB，brotli 后约 126KB），不调用 Worker；不要让课程广场的常规浏览重新依赖 API。额度设计见 [性能记录](performance-audit-20261114.md) 中“11 月 23 日”一节。
- `*.workers.dev` 上 Cloudflare Cache API 不生效，线上目前也没有接自定义域名，所以所有“靠边缘缓存省读取”的方案在现阶段都不成立。
- 静态目录由 `scripts/prepare-public-directory.mjs` 从核验过的 D1 导出生成，格式见 `shared/course-directory.ts` 的 `DirectorySnapshot`（version 2）。改格式要同时改生成脚本、`openDirectory`、测试，并重新生成快照。
- 检查命令：`npm run check`（类型检查、`node --test tests/*.test.mjs` 全部测试、前端构建、Worker dry-run）。当前 131 项测试全部通过，改动后应保持全绿，并为新行为补测试。
- 文档用中文；代码风格见 `.editorconfig`（UTF-8、LF、两空格）。TypeScript 严格模式，未使用变量会报错。
- 线上部署（`npm run deploy`）、线上 D1 迁移需由项目负责人确认后执行，实现者不要自行部署。
- `localStorage`/`sessionStorage` 读写都要包在 try/catch 里，存储不可用时页面仍要正常工作（参考 `web/catalog.tsx` 的视图切换写法）。

## 三、问题与方案（按建议顺序）

### P1 搜索结果没有相关度排序

**现象**：搜“数据结构”得到 53 门，按 ID 排序。完全同名的“数据结构”（十几门，分属不同学院）和“数据结构课程设计”“程序设计实践（C++和数据结构）”“算法与数据结构”交错出现。

**位置**：`shared/course-directory.ts` 的 `searchDirectory`。现在 `sort === 'default'` 时保持 `courses` 原顺序（即 ID 顺序），`name`/`rating`/`reviews` 三种排序在函数末尾分别处理。

**方案**：
1. 只在“有搜索词且排序为默认”时启用相关度排序；没有搜索词时保持原有顺序，避免影响现有测试和专业方案浏览。
2. 相关度分档（数字越小越靠前），代码和名称都参与：
   - 0：名称（NFKC、去空白、小写后）与搜索词完全相同，或课程代码完全相同，或命中别名代码（`aliasCodesForQuery`）
   - 1：名称以搜索词开头
   - 2：名称包含搜索词
   - 3：仅代码包含搜索词
3. 同档内依次按：评价数（有 `ratings` 时）降序 → 开课单位不是“待核实”的优先 → 名称长度升序 → ID 升序。
4. 排序在分页之前完成（现在的实现已是先过滤、排序，再 `slice`）。

**验收**：
- 新增测试：用小型合成快照断言“完全同名 → 前缀 → 包含 → 仅代码”的顺序，以及无搜索词时顺序不变。
- 真实快照搜“数据结构”，第一页前若干条全部是名称恰为“数据结构”的课程。
- `tests/course-directory.test.mjs` 现有断言全部通过。

### P2 记住用户的学院/专业并优先展示

**现象**：同名课程很多（全目录 2,559 个名称重复出现），学生每次都要靠卡片上一行小字分辨哪一门是自己学院的。

**方案**：
1. 用户在课程广场选择“培养学院”或“专业／班型”时，把学院与专业写入 `localStorage`（建议键名 `csu-my-plan`，值为 `{college, program}` 的 JSON）。在筛选区加一个可见的“设为我的专业／清除”提示，让用户知道被记住了、可以撤销。
2. P1 的相关度排序在同一分档内，把属于“我的学院最新方案”的课程排在前面（课程集合可用 `openDirectory` 返回的 `colleges`/`programs` 计算，逻辑参考 `searchDirectory` 里 `members` 的构建方式，取最新版本 `latestPlanYear`）。
3. 不自动替用户加筛选条件，只影响排序，避免用户以为“搜不到”。

**验收**：设置后搜索同名课程，本学院的条目排在同档最前；清除后恢复；隐私窗口（存储抛异常）下页面正常。

### P3 首页第一印象与贡献入口

**现象**：默认列表从 7 门无代码的种子课程开始，看起来像数据不全；全站只有 2 条评价，但首页没有引导用户去写评价。

**方案**：
1. 默认排序（无搜索词、无筛选）下，把“有课程代码且开课单位不是待核实”的课程排在前面，其余按原 ID 顺序跟在后面。实现位置同 P1，注意 `tests/course-directory.test.mjs` 中依赖默认顺序的断言（专业筛选场景下保持原顺序即可）。
2. 在 `web/catalog.tsx` 的 `catalog-intro` 区域增加一个简短的引导卡片，例如“选你的专业，评一门上学期的课”，点击后聚焦“培养学院”选择框或直接跳到已记住的专业（配合 P2）。已记住专业的用户显示“去评价 XX 专业的课程”。
3. 文案保持克制，不要做弹窗。

**验收**：无筛选打开首页，第一屏不出现“课程代码待补充”；引导卡片在手机上不超过约 120px 高。

### P4 文字对比度与字号

**现象**（在白色背景上实测）：

| 元素 | 样式位置 | 颜色 | 字号 | 对比度 |
| --- | --- | --- | --- | --- |
| 结果数“53 门课程” | `web/style.css` `.result-count`（约第 381 行） | `#7b8490` | 0.75rem（12px） | 3.41:1 |
| 课程代码 | `.card-code`（约第 549 行） | `#8c95a0` | 0.68rem（约 10.9px） | 3.03:1 |
| “显示 1–24 / 53 门课程” | `.catalog-bottom`（约第 644 行） | 约 `#84909d` | 约 11.2px | 2.93:1 |

普通文字需要至少 4.5:1。

**方案**：以上三处改用已有变量 `--muted`（`#616872`，白底约 5.9:1），课程代码字号提到至少 0.75rem。顺手用浏览器脚本或 axe 扫一遍其他使用硬编码浅灰色的地方（`grep -n "color: #[89a-f]" web/style.css`），一并改成变量。

**验收**：课程广场、详情页、写评价弹窗中所有正文文字对比度不低于 4.5:1。

### P5 手机端信息密度

**现象**（375px 宽）：顶部品牌与导航折成两行，约 120px；筛选区（类型标签、学院、专业、排序、更多筛选）约 300px；每张网格卡片约 160px 高，第一屏只能看到不到 1 张课程卡片，一屏最多约 4 张。

**位置**：`web/style.css` 的 `@media (max-width: 560px)`（约第 1236 行起，`.header-inner`、`.primary-nav`）与 `web/catalog-filters.tsx`。

**方案**：
1. 手机上把品牌与两个导航链接放在同一行（导航链接保持至少 44px 的点击高度）。
2. 手机上筛选区默认折叠为一行：“全部课程／专业课／公选课”标签 + 一个“筛选（已选 N 项）”按钮，点开后展开现有的选择框。已有筛选条件时显示已选标签，便于移除。可用 `<details>` 实现，保持无障碍可用。
3. 手机上默认用列表视图（`course-rows`），用户手动切换过则尊重 `localStorage` 中的 `csu-catalog-view`；同时压缩列表行的内边距。

**验收**：375×812 下第一屏至少能看到 3 门课程；键盘与读屏可以展开筛选；320px 宽无横向滚动。

### P6 课程详情页信息单薄（纯前端部分）

**现象**：详情页只有名称、代码、分享、学习资料、评价。学生无法确认“这门是不是我上的那门”，同名课程的评价也会分散。

**方案**（数据全部来自已加载的静态目录，不增加 API 调用；`web/directory-data.ts` 的 `useDirectoryCourse` 已在加载目录）：
1. 显示“出现在这些培养方案中”：列出包含该课程的专业／班型及版本年份（取各专业最新版本，最多显示若干个，可展开）。需要在 `loadDirectoryCourses` 中同时保留 `programs`，建一个“课程 ID → 方案列表”的索引。
2. 显示“同名课程”：名称规范化后相同的其他课程，附学院和代码，点击跳转。提示“请确认你上的是哪一门再评价”。
3. 开课单位为“待核实”时不显示该字段（现有列表卡片已这样处理）。

**验收**：打开“数据结构”任一条目，能看到所属方案和其他同名条目；对不在任何方案中的课程，这两块不显示空标题。

### P7 列表卡片看不到评分（需要后端配合，暂缓）

**现象**：`web/directory-data.ts` 只在排序为“评分优先／评价最多”时请求 `/api/courses/ratings`；默认排序下卡片底部只显示“查看课程评价”，用户看不出哪些课有人评过。

**原因**：`/api/courses/ratings` 一次读取约 4,100 行，而 `workers.dev` 上缓存不生效，每次课程广场访问都请求会很快耗尽 D1 额度。

**方案（二选一，需负责人确认后再做）**：
- A：接入自定义域名后，评分接口的边缘缓存生效，把缓存时间从 60 秒提高到 5 分钟左右，再在所有排序下加载评分。
- B：新增评分汇总表（课程 ID、平均分、评价数），在评价发布、修改、撤回、审核时更新；评分接口只读有评价的课程行。需要新迁移和对应测试，并检查 `src/moderation.ts` 中所有改变评价状态的路径。

### P8 评价维度只有总分（需要后端配合，暂缓）

**现象**：`course_reviews`（`migrations/0003_reviews.sql`）只有 1–5 总分和正文，选课时最关心的难度、给分、作业量、是否推荐都没有结构化信息。

**方案**：追加迁移，为评价增加若干可空的选填字段（例如难度 1–5、给分 1–5、作业量 1–5、是否推荐 0/1）；写评价表单（`web/review-form.tsx`）放进“补充选课背景（选填）”同一折叠区；详情页汇总区显示各维度的平均值与样本数（样本过少时不显示）。旧评价这些字段为空。涉及 API 校验、审核修改流程和测试，工作量较大，建议在 P1–P6 之后单独立项，并由负责人确认迁移。

### P9 分享与搜索引擎收录（低优先级）

**现象**：路由使用 `#/courses/2` 形式，页面 `<title>` 在前端设置，`web/index.html` 只有通用 description，没有 Open Graph 信息。微信等分享卡片只显示通用标题，搜索引擎无法收录单门课程。

**方案**：至少为 `web/index.html` 补充站点级 `og:title`、`og:description`、`og:image`。若要逐课程收录，需要改为路径路由并由 Worker 为每门课注入标题和描述，这会让每次页面打开都消耗 Worker 请求额度，现阶段不建议做。

## 四、建议的实施顺序

1. P1 + P2（同一个函数，一起做，纯前端，收益最大）
2. P4（只改样式，独立）
3. P3、P5（与 P1/P2 有交集：默认排序、记住的专业、手机筛选区）
4. P6（纯前端，需改 `web/directory-data.ts` 的目录索引）
5. P7、P8 等负责人确认后端方案；P9 视需要

每一项单独提交，提交信息说明行为变化；完成后在本文件对应条目下补一行“已完成：提交号、测试数”。

## 五、范围之外：已知的数据问题

以下问题来自 2026-11-23 的数据检查，属于目录数据本身，前端不要用推断去“修正”，否则会违反项目“缺少依据保留未知”的规则：

- 开课单位名称混杂：学院、系、教研室、专业名并存，11 个是逗号拼接，3 个带“(停用)”。
- 268 组同学院同名不同代码的课程，其中 128 组类别不一致。
- 17 个培养方案的最新版本早于 2020 年，29 个最新版本少于 10 门课（多为提取不全）。
- 153 门公选课都没有细分类别；代码首位数字疑似对应类别，但需要正式文件确认后才能补。

处理这些需要负责人逐项决定规则，再改数据并重新生成静态目录。
